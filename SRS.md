# Software Requirements Specification (SRS)
## Mitior 2.0 — Mitior Operating System (mOS)

**Standard Compliance**: IEEE Std 830-1998 Recommended Practice for Software Requirements Specifications

**Architecture Paradigm**: Local-First Autonomous Business Operating System with Express REST Persistence & Multi-Role Governance

## 1. Introduction

### 1.1 Purpose
This Software Requirements Specification (SRS) defines the complete functional, non-functional, security, ergonomic, data schema, and verification requirements for **Mitior 2.0 (Mitior OS)**. It serves as the authoritative engineering contract for developers, architects, quality assurance engineers, and executive stakeholders.

### 1.2 Scope
Mitior 2.0 is a distraction-free, local-first Business Operating System designed for high-growth organizations, SMEs, and enterprise execution teams. The platform unifies strategic alignment, operational workflows, standard operating procedures (SOPs), organizational accountability, KPI scorecards, 90-day sprint execution, customer enquiry tracking, and workspace licensing into a cohesive 10-node operational console:

1. **01. Overview (`overview`)**: Executive command center, real-time operational health vitals, telemetry charts, and quick-action dispatchers.
2. **02. Value Engine (`engine`)**: Interactive Growth, Fulfillment, and Innovation pipeline step builder with automated bottleneck detection and SOP linking.
3. **03. Playbooks (`playbooks`)**: Standard Operating Procedure (SOP) repository with step-by-step interactive checklists, owner assignment, and completion tracking.
4. **04. Team Canvas (`team`)**: Organizational Accountability Canvas (CABs), role capacity metrics, and live autogenerated reporting flowchart.
5. **05. Scorecard (`scorecard`)**: Weekly Key Performance Indicator (KPI) tracker with 4-week rolling trend analysis and automated status classification (`On Track`, `At Risk`, `Off Track`).
6. **06. Sprints (`sprints`)**: 90-Day Quarterly Rocks, Monthly Milestone breakdown, and Weekly Task execution canvas.
7. **07. Compass (`compass`)**: Strategic Clarity Compass defining Core Mission, 3-Year North Star, Core Values, 4C Strategic Anchors, and the Quantitative Decision Evaluation Matrix.
8. **08. Settings (`settings`)**: Workspace administration, multi-role governance, synchronization codes (`S-OS-XXXX-YYYY`), snapshot backups, PIN lock security, licensing, and JSON/CSV data portability.
9. **09. Enquiries (`enquiries`)**: Customer & stakeholder enquiry pipeline, SLA response tracking, and conversion funnel management.
10. **10. SRS Specs (`srs`)**: Interactive in-app IEEE 830 Software Requirements Specification viewer with instant keyword/ID filtering, category pills, 1-click Markdown download, and raw Markdown clipboard copy.

### 1.3 Definitions, Acronyms, and Abbreviations
- **mOS / Mitior OS**: Mitior Operating System v2.0.
- **CAB**: Core Accountability Bullet — a specific outcome owned by a position on the Team Canvas.
- **SOP**: Standard Operating Procedure — a structured playbook containing actionable checklist steps.
- **Fundi**: Technical & Systems Specialist role responsible for configuring Value Engine pipelines, authoring technical SOPs, and maintaining operational workflows.
- **Operator**: Frontline execution specialist responsible for completing SOP checklists, updating assigned KPIs, and executing weekly sprint tasks.
- **Auditor**: Read-only compliance and governance reviewer with full visibility across nodes, scorecards, and SRS specifications without destructive write privileges.
- **STK Push**: Safaricom Daraja Lipa Na M-Pesa SIM Toolkit payment prompt.
- **Sync Code**: Unique workspace synchronization token (`S-OS-XXXX-YYYY`) allowing team members to join and synchronize with an administrator's workspace node.

### 2.2 User Roles and Characteristics
Mitior 2.0 enforces a four-tier Role-Based Access Control (RBAC) model:

| Role ID | Role Title | Operational Authority & Permissions |
|---|---|---|
| `ceo` | **CEO (Executive Administrator)** | Full read/write/delete authority across all 10 nodes, workspace settings, licensing upgrades, security PIN governance, sync code issuance, team roster management, and factory reset. |
| `fundi` | **Fundi (Systems & Process Architect)** | Full read/write authority over Value Engine (`02`), Playbooks/SOPs (`03`), Sprint Canvas (`06`), and Enquiries (`09`); can propose KPI updates; restricted from destructive workspace resets or billing changes. |
| `operator` | **Operator (Execution Specialist)** | Focused execution authority: can check off SOP checklist steps, log weekly KPI scorecard actuals, update assigned sprint tasks, and manage enquiries; restricted from deleting core engine nodes, deleting team members, or altering workspace security/billing settings. |
| `auditor` | **Auditor (Compliance & QA Reviewer)** | Strict read-only inspection authority across all 10 nodes, analytics, audit logs, and the interactive SRS viewer (`10. SRS Specs`), plus allowed to export compliance reports and SRS documentation. All mutating actions are disabled. |

*(Note: Legacy `'employee'` role profiles automatically map to `operator` for backward compatibility.)*

### 2.3 Operating Environments
- **Client Runtime**: Any modern Evergreen browser (Chrome 115+, Safari 16.4+, Edge 115+, Firefox 115+) across Desktop (`1280x800` to `4K`) and Mobile/Tablet (`375x667` to `1024x768`) viewports.
- **Server Runtime**: Node.js `v18.0.0+` (tested on `v20+` / `v22+`), macOS, Linux, or Windows 10/11.
- **Typography & Rendering**: Preloaded Google Fonts (**Plus Jakarta Sans** for body, controls, tables, and metrics; **Outfit** for headings, titles, and badges; **JetBrains Mono** for code/telemetry identifiers) with `font-display: swap` for sub-800ms cold render performance.

### 2.4 Data Sovereignty & Local-First Custody
All operational data resides on the user's local storage (`localStorage` + `server_db.json`). External network requests are strictly opt-in (e.g., live Safaricom Daraja STK Push or Stripe checkout when API keys are configured in `.env`; otherwise deterministic local sandbox simulation is used).

## 3. Functional Requirements

### 3.1 Navigation, Typography & Ergonomics (`[FR-NAV]`)
- **FR-NAV-01 (10-Node Navigation Architecture)**: The system shall provide seamless switching across all 10 operational nodes (`01. Overview`, `02. Value Engine`, `03. Playbooks`, `04. Team Canvas`, `05. Scorecard`, `06. Sprints`, `07. Compass`, `08. Settings`, `09. Enquiries`, `10. SRS Specs`) via the top navigation bar and the persistent bottom dock.
- **FR-NAV-02 (Persistent Floating Bottom Dock)**: The system shall render a pinned floating quick-access dock (`bottom-3 left-1/2 -translate-x-1/2 z-40`) visible at all times across workspace views, providing 1-click node switchers, a `"Menu"` trigger that opens the workspace navigation sheet modal regardless of scroll position, a dark/light theme switcher, and a smooth `"Return to Top"` action.
- **FR-NAV-03 (Fresh Modern Typography)**: The system shall use **Plus Jakarta Sans** for all body text, controls, tables, and metrics, and **Outfit** for all headings, titles, and badges, preloaded via Google Fonts with `font-display: swap`.
- **FR-NAV-04 (Zero-Scrollbar Ergonomics)**: The system shall apply compacted vertical padding, optimized grid gaps, and global scrollbar suppression utilities (`no-scrollbar`, `scrollbar-gutter: stable`) to prevent horizontal overflow and excessive vertical scrollbars on standard viewports.
- **FR-NAV-05 (Zero Browser Alerts)**: The system shall never invoke blocking browser `window.alert()` dialogs; all user notifications, validations, clipboard confirmations, and error states shall render via non-blocking inline feedback banners or toast banners.
- **FR-NAV-06 (Interactive SRS Viewer Node)**: The system shall provide `SrsDocumentView.tsx` accessible from `"10. SRS Specs"` in the navbar, bottom dock, and `Settings → 10. SRS Specification`, featuring instant keyword search across requirement IDs/categories, category filtering, a 1-click `"Download SRS.md"` export button, and a `"Copy Raw Markdown"` button.

### 3.2 Authentication, RBAC & Session Security (`[FR-SEC]`)
- **FR-SEC-01 (Account Registration & Authentication)**: The system shall support local account sign-up (`/api/auth/signup`), sign-in (`/api/auth/login`), session validation (`/api/auth/me`), and logout (`/api/auth/logout`) using Bearer session tokens with 7-day rolling expiration.
- **FR-SEC-02 (Authenticated Password Reset & 6-Digit Recovery Code)**: The system shall require either a verified 6-digit recovery code (`/api/auth/verify-code`) or an active authenticated session before permitting password resets on `/api/auth/reset-password`, preventing unauthenticated account takeover.
- **FR-SEC-03 (Four-Role Governance)**: The system shall support `CEO`, `Fundi`, `Operator`, and `Auditor` roles during workspace initialization and inside `SettingsView`, enforcing role-appropriate action guards in the UI and API.
- **FR-SEC-04 (Cryptographic Security PIN Lock)**: The system shall allow configuring a 4-to-6 digit Security PIN (`/api/security/pin`) stored as a cryptographic hash on the server, and shall lock the workspace UI behind a PIN verification screen when locked.

### 3.3 Value Engine Pipeline (`[FR-ENG]`)
- **FR-ENG-01 (Multi-Pipeline Visualization & CRUD)**: The system shall manage Growth, Fulfillment, and Innovation engine nodes with stage classifications (`Trigger`, `Process`, `Power Step`, `Output`), conversion rates, duration metrics, and accountable owners.
- **FR-ENG-02 (Automated Bottleneck Diagnostics)**: The system shall automatically flag and highlight pipeline bottlenecks where conversion rate falls below threshold (`< 50%`) or status is marked `Bottleneck`, surfacing remediation links to associated Playbooks.
- **FR-ENG-03 (Tier Capacity Enforcement)**: The system shall enforce node capacity limits according to license tier (`Free`: 10 nodes, `Starter`: 20 nodes, `Professional`/`Enterprise`: unlimited) with clear inline upgrade prompts.

### 3.4 Standard Operating Procedures / Playbooks (`[FR-SOP]`)
- **FR-SOP-01 (Playbook Repository & Search)**: The system shall allow creating, editing, searching, filtering, and deleting SOP Playbooks categorized by department (`Growth`, `Fulfillment`, `Operations`, `Finance`, `Culture`) and linked to Value Engine steps.
- **FR-SOP-02 (Interactive Step Checklists & Progress)**: Each Playbook shall support ordered checklist steps (`PlaybookStep`) that users (CEO, Fundi, Operator) can toggle complete/incomplete, dynamically recalculating playbook completion percentages and logging activity telemetry.

### 3.5 Team Canvas & Organizational Hierarchy (`[FR-ORG]`)
- **FR-ORG-01 (Accountability Roster & CAB Management)**: The system shall manage Team Member profiles including job title, department, reporting manager, Core Accountability Bullets (CABs), KPI ownership, capacity utilization, and hiring vacancy status (`Active` vs `Vacant`).
- **FR-ORG-02 (Founder Protection Constraint)**: The system shall prevent deletion of the Founder/CEO root profile and display an inline feedback banner explaining the governance constraint if deletion is attempted.
- **FR-ORG-03 (Live Autogenerated Org Hierarchy Chart)**: The system shall dynamically construct and render an interactive parent-child reporting tree (`OrgHierarchyChart.tsx`) from team manager relationships with 1-click member drill-down.

### 3.6 Weekly Scorecard & Telemetry (`[FR-SCR]`)
- **FR-SCR-01 (KPI Metric Tracking & Status Calculation)**: The system shall track weekly KPI metrics with target benchmarks, current actuals, unit labels (`%`, `$`, `KES`, `#`, `hrs`, `days`), accountable owners, and automated status calculation (`On Track`, `At Risk`, `Off Track`).
- **FR-SCR-02 (4-Week Rolling Trend Visualization)**: Each scorecard metric shall maintain a 4-week rolling history array (`W1`–`W4`), rendering sparkline/trend indicators and feeding executive telemetry charts on `DashboardOverview`.

### 3.7 90-Day Sprint Canvas (`[FR-SPR]`)
- **FR-SPR-01 (Quarterly Rocks & Monthly Milestones)**: The system shall manage 90-day Quarterly Rocks, 30-day Monthly Milestones (`M1`, `M2`, `M3`), and weekly sprint focus themes with progress bars and owner assignments.
- **FR-SPR-02 (Weekly Sprint Task Board)**: The system shall allow adding, toggling (`Todo`, `In Progress`, `Done`), filtering, and deleting weekly execution tasks tied to team members and quarterly rocks.

### 3.8 Strategic Clarity Compass (`[FR-CMP]`)
- **FR-CMP-01 (Strategic North Star & 4C Anchors)**: The system shall allow viewing and editing the organization's Mission Statement, 3-Year North Star Target, Core Values, and 4C Strategic Anchors (`Company`, `Customer`, `Culture`, `Competition`).
- **FR-CMP-02 (Quantitative Decision Evaluation Matrix)**: The system shall provide an interactive Decision Evaluation Matrix inside `ClarityCompassView.tsx` enabling leaders to score strategic proposals across Company, Customer, Culture, and Competitive alignment (`1–5` scale), automatically computing a `0–100%` alignment score and `GO` (`>= 70%`) vs `NO-GO` (`< 70%`) verdict persisted in workspace state.

### 3.9 Customer Enquiries & SLA Pipeline (`[FR-ENQ]`)
- **FR-ENQ-01 (Enquiry Lifecycle Management)**: The system shall provide a dedicated Enquiries node (`09. Enquiries`) to log, search, filter, and transition customer enquiries across `Pending`, `In Progress`, `Resolved`, and `Archived` states with priority levels (`Low`, `Medium`, `High`, `Urgent`) and SLA response time tracking.

### 3.10 Workspace Settings, Sync Codes & Portability (`[FR-SET]`)
- **FR-SET-01 (Bidirectional Sync Code Hub)**: Administrators shall be able to generate workspace Sync Codes (`S-OS-XXXX-YYYY`) via `/api/sync-codes` that snapshot the active workspace payload on the server; team members joining via `/api/sync-codes/verify/:code` shall receive both the project metadata and the synchronized workspace state.
- **FR-SET-02 (Server Snapshot Backups & Restore)**: The system shall support creating server-side workspace snapshots (`POST /api/backups`), listing snapshots (`GET /api/backups`), and restoring any snapshot (`GET /api/backups/:id`) into the active workspace.
- **FR-SET-03 (Data Export & Import Portability)**: The system shall support full workspace JSON export/import and structured CSV clipboard/file export of operational tables.

### 3.11 Licensing, Billing & Offline Packaging (`[FR-LIC]`)
- **FR-LIC-01 (Dual Payment Gateway & Sandbox Simulator)**: The system shall provide `CheckoutPortal.tsx` supporting Lipa Na M-Pesa STK Push (`/api/checkout/mpesa-push`, `/api/checkout/status/:id`) and Credit/Debit Card checkout (`/api/checkout/card-pay`), automatically falling back to a realistic local sandbox simulator when external gateway keys are absent.
- **FR-LIC-02 (Authenticated Billing Ledger)**: The system shall record all completed licensing transactions per user and return them via `GET /api/checkout/history` with valid Bearer authentication headers.
- **FR-LIC-03 (Enterprise Offline Bundle Generator)**: The system shall provide an interactive offline workstation bundle generator (`MitiorOS-Enterprise-Desktop-Workstation.zip`) containing standalone launch scripts and documentation.

## 4. Non-Functional Requirements

### 4.1 Performance Requirements (`[NFR-PER]`)
- **NFR-PER-01 (Cold Render Speed)**: Initial application shell and preloaded fonts (`Plus Jakarta Sans` and `Outfit` with `font-display: swap`) shall render in under `800ms` on local workstation hardware.
- **NFR-PER-02 (Node Switching Latency)**: Switching between any of the 10 workspace nodes shall complete in under `50ms` with zero layout shift (`scrollbar-gutter: stable`).
- **NFR-PER-03 (SRS Search Responsiveness)**: Keyword and category filtering in `SrsDocumentView.tsx` shall filter requirements instantaneously (`< 16ms` per keystroke) entirely client-side.

### 4.2 Reliability & Data Integrity (`[NFR-REL]`)
- **NFR-REL-01 (Crash-Safe Atomic Persistence)**: All client state mutations shall immediately persist to `localStorage` and synchronize to `server_db.json` without data loss across browser refreshes or server restarts.
- **NFR-REL-02 (Graceful Corruption Recovery)**: If `localStorage` or `server_db.json` encounters malformed JSON, the system shall log a structured warning and fall back to a valid default schema without crashing the UI or Express process.

### 4.3 Security Requirements (`[NFR-SEC]`)
- **NFR-SEC-01 (Credential & PIN Hashing)**: User passwords and security PINs shall never be stored in plaintext in `server_db.json`; salted cryptographic SHA-256/HMAC hashing shall be enforced.
- **NFR-SEC-02 (Server-Side Authorization Enforcement)**: All mutating `/api/sync-codes`, `/api/backups`, `/api/security`, and `/api/checkout` endpoints shall validate the caller's Bearer session token via `requireLoggedInUser` and enforce tier/role constraints via `requirePaidTier` where applicable.
- **NFR-SEC-03 (Secret Isolation)**: No third-party API secrets (`MPESA_CONSUMER_SECRET`, `STRIPE_SECRET_KEY`, `GEMINI_API_KEY`) shall ever be exposed in client bundles or returned by `/api/checkout/config`.

## 5. Data Schemas

### 5.1 Core Workspace State Schema (`src/types.ts`)
```typescript
export type UserRole = 'ceo' | 'fundi' | 'operator' | 'auditor' | 'employee';

export interface EngineNode {
  id: string;
  title: string;
  stage: 'Trigger' | 'Process' | 'Power Step' | 'Output';
  pipeline: 'Growth' | 'Fulfillment' | 'Innovation';
  owner: string;
  conversionRate: number;
  durationDays: number;
  status: 'Optimal' | 'Needs Attention' | 'Bottleneck';
  linkedPlaybookId?: string;
  description: string;
}

export interface PlaybookStep {
  id: string;
  title: string;
  completed: boolean;
  owner?: string;
}

export interface Playbook {
  id: string;
  title: string;
  category: 'Growth' | 'Fulfillment' | 'Operations' | 'Finance' | 'Culture';
  ownerId: string;
  lastUpdated: string;
  completionRate: number;
  content: string;
  steps: PlaybookStep[];
  linkedEngineNodeId?: string;
}

export interface DecisionEvaluation {
  id: string;
  title: string;
  date: string;
  companyScore: number;     // 1-5
  customerScore: number;    // 1-5
  cultureScore: number;     // 1-5
  competitiveScore: number; // 1-5
  totalPercentage: number;  // 0-100
  status: 'GO' | 'NO-GO';
  notes: string;
}
```

### 5.2 Server Persistence Schema (`server_db.json`)
- `users`: `Record<string, UserAccount>` (id, name, email, passwordHash, createdAt, licenseTier, recoveryCode)
- `sessions`: `Record<string, SessionRecord>` (token, userId, email, name, expiresAt)
- `syncCodes`: `Record<string, SyncCodeRecord>` (code, projectName, creatorName, projectId, description, workspaceData, createdAt)
- `backups`: `Record<string, BackupSnapshot[]>` (id, timestamp, workspaceName, dataCount, payload)
- `security`: `Record<string, SecurityProfile>` (pinHash, isPinEnabled, updatedAt)
- `transactions`: `Record<string, CheckoutTransaction>` (checkoutRequestId, userId, phone/card, amount, planName, status, receiptNumber, timestamp)
